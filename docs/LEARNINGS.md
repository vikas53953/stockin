# Learnings

What this project has taught us about building it, newest at the bottom.
Each entry is a moment something went wrong or the owner pushed back, the
lesson, the rule it produced, and what that rule has caught since. Add entries
at every sprint retro and whenever the owner corrects the process. The rules
themselves are in `CLAUDE.md`; their history is in [PIPELINE.md](PIPELINE.md).

## Sprint 1, drop 1 (2026-11-17)

### 1. Passing tests did not mean a working import
- **What happened:** pytest was green, but the first run of the installed `stockin import cas` printed casparser enums as `TransactionType.PURCHASE`, because the library returns enum members and plain strings in different paths.
- **Lesson:** the real surface finds what unit tests built from our own assumptions cannot.
- **Rule:** a change is done when it has run on the installed binary through the `verify` skill (PIPELINE #1).
- **Caught since:** the busy-port crash in `stockin web`, phone overflow on the reconcile table.

### 2. The author is a poor judge of their own change
- **What happened:** three PRs that looked finished failed independent verification before the PDF work: #3 (the docs promised `--json` on every command, `version` had none), #4 twice (the fold depended on the order facts arrived in, then a phantom holding after a flagged zero), and #9 (a PDF error class the check missed).
- **Lesson:** an agent that did not write the code must verify it, and its verdict, not the author's, gates the merge.
- **Rule:** independent verifier, head-SHA guard, at most two fix-forwards (PIPELINE #2).
- **Caught since:** every fix in #6, #7, #9 and #10 came from verifier notes.

### 3. A claim was written before the check ran
- **What happened:** the #10 PR body described a browser check that had not been run yet. It passed when run, but the order was wrong.
- **Lesson:** a check reported before it runs is a fake green, even if it later passes.
- **Rule:** never claim a check that has not run; evidence is attached, not described (PIPELINE #4, #7).

### 4. The owner asked whether we had tested it ourselves
- **Pushback:** the owner was handed a checklist to test real CAS PDFs. No statement-layout PDF had ever been imported: the imports had used casparser JSON, and the only PDFs through the app were a blank one, junk bytes and an encrypted dummy, all checking rejections.
- **Lesson:** never ask the owner to be the first person to try something. The owner's run is confirmation, not discovery.
- **Rule:** an agent runs the owner's exact steps first, as an end user, on realistic password-protected synthetic PDFs, in a browser (PIPELINE #6).
- **Caught since:** TDS on an IDCW payout rejected the whole statement (#12); cost shows unknown for funds held before the statement period; the checklist itself gave the wrong CDSL password advice.

### 5. Test the instructions, not just the app
- **What happened:** running the owner's checklist ourselves showed two wrong instructions: "CDSL password is sometimes PAN + DOB" (CDSL's FAQ says PAN), and "cover at least 6 months" (cost needs the statement to start before the first investment).
- **Lesson:** a UAT checklist is part of the product and needs the same testing.
- **Rule:** covered by agent-first UAT; checklist fixes ship with the run that found them.

### 6. Make fake green impossible
- **Pushback:** the owner asked for before and after screenshots, and then video, so that no agent can report a pass without proof.
- **Lesson:** evidence must be something a reader can check: files with hashes, not a sentence.
- **Rule:** before/after screenshots, video for multi-step browser flows, raw output with exit codes, sha256 in the verdict; no evidence means no merge (PIPELINE #7, #8).

### 7. A new test can pass for the wrong reason
- **What happened:** the first set of property tests passed with the #4 fix reverted, so they did not guard against the bug that motivated them.
- **Lesson:** a test only counts once you have seen it fail on the bug it is meant to catch.
- **Rule:** property tests are a gate, and every new test is mutation-checked by reverting the fix (PIPELINE #5).
- **Caught since:** the gap itself; a demat property was added and now catches the revert.

### 8. Small drops, real QA between them
- **Pushback:** no large codebase without real QA; split features into small batches the owner tests end to end.
- **Lesson:** merged is not released. Main can move fast; a version tag waits for the owner.
- **Rule:** drop 1 / drop 2 split, `v0.N` tag only after the owner's run, retro at sprint end (PIPELINE #3).

### 9. The repository is public
- **Lesson:** every fixture, screenshot and log could be read by anyone. Synthetic data only, invented names, a fake PAN; the owner never sends a PDF or password.
- **Rule:** hard rules in `CLAUDE.md`; evidence screenshots show synthetic data only.

### 10. A fix can be wrong in a case nobody looked at
- **What happened:** #12 fixed TDS on an IDCW payout, but also took TDS off a reinvested IDCW, whose amount is already net. The verifier's own property test found it, shrunk to a 1-paisa example. Before the fix such a CAS was rejected; after it, it would have imported a wrong amount silently, and re-importing the same file cannot correct a stored fact.
- **Lesson:** the riskiest bug turns a loud rejection into a quiet wrong number.
- **Rule:** fix-forward with a test asserting Income equals the net Buy; the verifier mutation-checks it.

### 11. Commit before a mutation check
- **What happened:** during a mutation check, `git checkout -- file` restored the file to the last commit and wiped the uncommitted fix along with the mutation. It was noticed from `git diff --stat` and re-applied.
- **Lesson:** mutations are reverted with git, so the real change must already be in git.
- **Rule:** commit (a WIP commit is fine) before injecting mutations.

### 12. Properties can look strong and still miss most bugs
- **What happened:** the #11 verifier injected 10 bugs of its own; the new properties caught 4. One property could not fail (share + rest equals the total by construction), about half the retract examples checked nothing, exact .5 ties were almost never drawn, and nothing checked money in the ledger.
- **Lesson:** the author's mutation check uses bugs the author already thought of; the verifier's finds the ones they did not.
- **Rule:** every new or changed test is mutation-checked by the verifier with its own mutations (PIPELINE #10).
- **Caught since:** the #14 verifier confirmed five of the six gaps closed, including a ledger read (`Ledger._latest`) that had no test at all; the sixth (Indian grouping) is caught by a unit test. Its own new mutations then found per-lot proceeds unchecked (#15).

### 13. History needs checking too
- **What happened:** the first version of this file and PIPELINE.md said two PRs had failed verification; the record shows #3 and #4's first FAIL as well. One claim ("no PDF had ever gone through the app") overstated what was true.
- **Lesson:** a log written from memory drifts from the record, and a flattering log teaches the wrong lesson.
- **Rule:** docs about our own process are verified against PR comments and git history (PIPELINE #11).
- **Caught since:** #19 FAIL. A new lesson said none of the ten apps studied shows SIP discipline or long-term lot dates; the teardowns it cited show Zerodha Console, Value Research and Kuvera covering parts of both, and the catalogue had only said "none of four, inferred". The same claim had gone to the owner and was corrected.

### 14. Evidence files can change after you hash them
- **What happened:** the #13 verifier found that the project share adds a metadata chunk to PNG screenshots a few seconds after they are copied. Hashes taken right after the copy failed `sha256sum -c` twenty seconds later, though the pixels were identical.
- **Lesson:** a hash proves nothing if the file can legitimately change under it; the evidence store has to be settled before it is fingerprinted.
- **Rule:** fingerprint evidence with `evidence_hash.py`, which hashes every byte of a PNG except the share's own `caBX` chunk, and only where the share puts it (PIPELINE #13).
- **Caught since:** three fixes failed verification on #16. "Wait until two hashes 30 seconds apart agree" passed, then the share rewrote every PNG at about two minutes (other times it took eleven, twenty-seven and forty-two; there is no known upper bound): timing rules for a process you do not control are guesses. Then hashing only the image data let the verifier add APNG frames that make an "after" screenshot show the "before" page, with the fingerprint unchanged. Then skipping `caBX` anywhere let a `caBX` placed between IDATs hide the bottom of a screenshot. Exclude exactly what you must, and nothing more. The fourth attempt skips it only as the second chunk and passed (PASS+NOTES).

### 15. Agent-first UAT ran on the wrong operating system
- **What happened:** the owner ran the checklist on Windows. Its data-folder step, `mkdir -p ~/stockin-data && $env:STOCKIN_DATA=...` (the Unix line with a Windows note to swap `export` by hand), fails to parse in PowerShell: 5.1 has no `&&`, and `$env:X=...` after `&&` is not valid in 7 either. Its install line also used a `git+` URL, which needs Git installed. Our own UAT run had used Linux and bash only, so it passed. (The checklist lives in the project files, not in git, so its old text is quoted from the owner's error message.)
- **Lesson:** running the owner's steps first only counts if it runs them where the owner runs them: same OS, same shell, same version.
- **Rule:** the checklist gives one command per line per OS, with no hand edits. CI runs its PowerShell lines on `windows-latest` in both PowerShell 5.1 and 7 (PIPELINE #14); outside CI, lint them with PSScriptAnalyzer `PSUseCompatibleSyntax`/`PSUseCompatibleCommands`. On the old line it reported four findings: a parse error, `&&` (not in 5.1), `mkdir` (not in 5.1) and `-p` (not on 7.0); on the new lines, none. Install now uses the zip URL, so Git is not needed.

### 16. Synthetic statements are not the real risk
- **What happened:** the owner has no CAS of his own yet, so he is testing drop 1 on our synthetic PDFs. They copy the CAMS, NSDL and CDSL layouts as the parser expects them, not as measured from a real statement.
- **Lesson:** a pass on files we made shows the app agrees with our idea of the layout, not with the issuers'. Whether a real CAS imports correctly is still open.
- **Rule:** every report about drop 1 says it used synthetic PDFs. The real-statement risk stays open (last row of the drop 1 retro) until a real CAS has been imported end to end. (Whether that should gate `v0.1` is the owner's call and has not been asked yet.)

### 17. The owner wants numbers turned into learnings
- **What happened:** after using drop 1, the owner said plain tables are not enough. Data should be shown visually, and Stockin's moat is translating numbers into patterns the user understands and learns from. A study of ten apps (`/mnt/project-files/stockin/re/`) found the pattern most clearly in INDmoney (a chart, one sentence and a "Learn how" link) and Tickertape (a band name and one next step). Some apps already cover parts of behaviour and tax timing: Zerodha Console lists each lot's days held and long- or short-term status, Value Research shows unrealised short- and long-term gains, and Kuvera's Discipline lens tracks SIP behaviour, though how it looks is unknown. A CAS alone has the data for both.
- **Lesson:** the product is the explanation, not the table. An explanation that disagrees with its own chart is worse than none (one app's own mock-up says 32% in the sentence and 35% in the legend).
- **Rule:** insights are computed by code from the same numbers as their chart, and a test asserts the sentence and the chart agree. No model writes a number. Design directions are shown to the owner as options before the UI is built.

## Sprint 1, drop 2 (2026-11-17)

### 18. "Rejected cleanly" has to cover every way a download breaks
- **What happened:** PR #18 (end-of-day prices) failed verification six times. The first FAIL: a truncated bhavcopy zip (`BadZipFile`) and a connection closed mid-download (`IncompleteRead`, an `HTTPException`, not an `OSError`) ended in a traceback, and in `prices fetch` the crash also threw away the AMFI prices that had downloaded. Four injected bugs survived. The fix caught `BadZipFile` and retried `HTTPException`. The second FAIL: the verifier damaged a real NSE zip 4,587 ways (cuts, overwrites and single-byte changes) and 24 copies still escaped (`RuntimeError` for a flipped "encrypted" bit, `ValueError` for a bad directory offset); one survivor (a 404 inside the real `_get`) was "tested" only through a stub that replaced `_get`. The third FAIL: the same kind of damage to a plain `.csv` raised `csv.Error` (33 of 5,550 copies of the real file) from the CSV reader, which neither earlier fuzz had touched because both fuzzed only the zip. The owner allowed a third fix. The fourth FAIL: nothing crashed on a real download any more, but one lost comma in a plain CSV's header shifted every column and the day's low was stored as the close with exit 0 (106 of 1,821 header damages), because the fuzz test only asked "parses or is rejected", and a parse with wrong numbers passes that. A damaged page in `prices.db`, a 14-digit price and a crafted short row still ended in tracebacks. The owner allowed a fourth fix. The fifth FAIL: the fourth fix held (a shifted column is rejected), but a plain CSV or NAVAll has no checksum, so one changed byte can leave a valid file with a wrong price: `1108.60` became `1108260`, a trade date became year 9026, and a byte on another fund's line turned its ISIN into a held fund's with a check digit that still passed. That cannot be detected in general. The defect was that it stuck: `prices.db` kept the larger of two prices for a day, readers took the latest date, and no date was too late, so importing the right file afterwards changed nothing and `doctor` reported "latest 9026-11-17". The repo's own every-byte test missed the wrong-ISIN case because it counted an ISIN created by the damage as part of the damaged line. Ten of 22 reverted checks and four of eight injected bugs survived. After two failed fix rounds by the same author the owner's rule sent the failing cases to a different author. That fix makes a price file replace what is stored for its source and day, with readers taking each source's newest file; rejects a date after today, a bhavcopy row for another day and a NAV more than 30 years older than its file; and holds back a price more than double or less than half the last one until the owner accepts it. The sixth FAIL (verifier 6, on that fix): the parsers held, but `prices.db` itself accepted a row dated after today. One flipped byte in the file (2026 to 2029 in a row's file day) made that row the newest file for ever, so no later import could replace it and `doctor` said "latest 2029-11-17". The guard against future dates had been put on the way in (the parsers) but not on the place the dates are kept. Under the owner's rule (after two FAILs, escalate once, then re-scope instead of asking for another try) #18 was closed and the same change, plus a store that refuses any row dated after today in India, went up as #21. Its first verifier FAILed it on two older gaps in how `prices.db` is checked when opened, which verifier 6 had also missed: a non-UTF-8 byte in the table's schema text crashed every command with `UnicodeDecodeError` (only SQLite's own errors were caught), and one byte in an ISIN key put rows out of key order, so lookups returned a stale row while every row still looked valid and `doctor` said ok. The fix runs SQLite's full `integrity_check` on open and treats a decode error like any other damage. Its second verifier FAILed it on one more value the open-time scan let through: SQLite's `date()` accepts year 0000 and Python's `date` does not, so a stored NAV date changed from 2026 to 0000 (three bytes) passed the scan and then crashed `holdings`, `prices import` and `prices fetch` with `ValueError` while `doctor` said ok, and the scan had no lower bound at all where the parser refuses a NAV more than 30 years older than its file. After two FAILs the case went to a different author under the owner's rule: the scan now refuses a date before the first day Python can hold and a NAV more than 30 years older than its file, and any `ValueError` from turning a stored row into a value is reported as damage. The third verifier on #21 found only crafted cases, none reachable by damaging a real file's bytes: a price file dated 0001-01-01 crashed `prices import` (and with `--accept-jumps` was stored), and a table with Stockin's column names but no NOT NULL let a NULL date crash every read. Each round had closed one instance and the next found its neighbour, so #21 was closed and re-scoped as #22 to close the classes: `prices.db` must hold exactly the table Stockin creates (constraints included, nothing else), ISINs must have an ISIN's shape, and one oldest file day (1994, NSE's first year) bounds both parsers and the store. #22 passed its fourth verifier (PASS+NOTES) and merged on 2026-11-19 (lesson 21).
- **Lesson:** a parser's error contract is every exception each layer under it can raise (zip, decompression, text decoding, the CSV reader), not the ones we have seen. Fuzz each input form the code accepts, not only the one fetch uses. A test that stubs out the code under test does not test it. "Did not crash" is not "did not lie": a fuzz test must also check what a damaged file is allowed to change. For a file without a checksum, "wrong values never get in" is a bar no parser can meet, and five rounds were spent approaching it. The bar that can be met is "undoable": whatever a damaged copy stored, importing the right file leaves the database exactly as if the damaged one had never been imported, and values no real file has are rejected. When fixes keep finding neighbours of the last bug, the check was written per instance: state the class ("exactly our table", "only values a real file has, at both ends") and check that.
- **Rule:** a parser of downloaded files gets a fuzz test per accepted input form that changes every byte of a fixture and asserts each copy is rejected or is undone exactly by importing the right file afterwards (and the test checks that some damage did get in); a file's structure (field count per row, value ranges) is checked, not assumed; one data source failing in any way never costs another's results. A store of downloaded data lets the last import of a file's day win, so the right file is always the correction; it never ranks two values for the same day by size or date. Tests for a function drive that function, with only the network and the clock faked. A bound checked where data comes in is also checked where it is kept, because the store can be damaged too. A file opened from disk is checked with the database's own full integrity check, not only a scan of its values, and a database error or a value error while reading it or turning what it holds into a value (not only the database library's errors) becomes the "damaged" message. The check that a stored value is real is made with the type the program reads it into, or is backed by one that is: two date libraries do not agree on what a date is.
- **Caught since:** nothing yet; the rule's first fuzz runs, and the first "undone by the right file" runs, are part of #18 itself.


### 19. Label a fact where it is known; don't guess it later
- **What happened:** PR #20 (insights) failed verification three times. The second fix-forward told reinvested dividends apart from new money by pairing a Buy with an Income of the same amount on the same day. The third FAIL showed that a real CAS adds stamp duty to the reinvestment's Buy (₹800.04 against an Income of ₹800), so the pair broke: the app said "₹800 paid out as dividends" and "All 4 SIP instalments paid" when one month was missed. The same guess also took a payout that equalled the SIP amount for a reinvestment. The tests used reinvestments without a stamp-duty row, so nothing caught it. The owner allowed a third fix.
- **Lesson:** a heuristic that rebuilds a fact the input already stated breaks on the first real detail the test data left out. The importer saw the row type `DIVIDEND_REINVEST`; the insight had only amounts.
- **Rule:** when a later step needs to know what a row was, the importer records it on the fact, and test histories generate the real rows that come with it (here stamp duty after a reinvestment). A new field with a default is left out of the canonical JSON, so earlier fact ids stay the same, and a test pins that.
- **Caught since:** nothing yet. The fix passed verification (PASS+NOTES) and #20 merged on 2026-11-19.

### 20. A new surface inherits every error the layer under it can raise
- **What happened:** PR #23 (home screen) failed its first verification. The page caught `PricesDamaged`, which is raised only when prices.db fails to open. Damage inside rows (a bad date, a bad source, a text price, flipped bytes) is raised later, while rows are read, as `ValueError` or `sqlite3.DatabaseError`. The verifier damaged prices.db 44 ways and 16 gave HTTP 500, on a page that loaded fine before the PR. The PR's own test wrote junk bytes, which only exercises the open path. The same miss reached #25 (holding page). Separately, #24's `stockin thesis set` caught damage when theses.db opened but not when it was written.
- **Lesson:** this is lesson 18 one layer up. When a page or command starts reading a store, it takes on that store's whole error contract, opening and reading and writing. A test that damages only the file header tests only the open.
- **Rule:** a surface that reads a store gets tests for damage inside rows (one per column kind) and a seeded byte-flip fuzz of a real file. It maps exactly the store's damage exceptions (`sqlite3.DatabaseError`, `ValueError`) to a notice. A test pins that any other exception still surfaces as a bug.
- **Caught since:** nothing yet. The fixes passed verification (PASS+NOTES on #23 and #25, PASS on #24) and #23, #24 and #25 merged on 2026-11-19.

### 21. "Undoable" has to hold for a file cut short, and the fix for that must not break it for a changed byte
- **What happened:** the second verifier on #22 (the first died on a billing error) FAILed it on two realistic cases. One zeroed byte at offset 104 of a real `prices.db` makes SQLite read an empty schema, and the open-time check treated "no tables" as a new file, so the next import wrote into a damaged file. And a NAVAll download or copy that stops at a line end still parses (168 of 1,518 cuts of the real 17 Nov file did), with fewer funds; importing it after the whole file replaced that day and deleted the price of every held fund it no longer listed (two rows in the verifier's run), with exit 0. The right file restored them, so it met the letter of lesson 18, but nothing told the owner to import it. A first attempt, never pushed, made every import keep rows it did not list; it failed lesson 18's own property in the local test run, because a damaged copy's extra row would then survive the right file. The fix that was pushed moved the keeping to the command: a held fund's price already stored for the day, and missing from the new copy, was kept (`KEPT`, exit 1), with `--accept-jumps` to store the file as it is. The third verifier FAILed that (R3). One changed byte in the real 18 Nov bhavcopy (`INF109KC10V2` to `INF109KC10C2`, the check digit still valid) stored an ETF's close as the price of a held mutual fund the bhavcopy never lists, 54% too high and inside the 2x jump bound. Importing the right bhavcopy then printed `KEPT` and exited 1, and the wrong price stayed; "download it again", the printed hint, did the same; only `--accept-jumps` cleared it, a flag that now meant two things. The build before the fix had restored the price on the first import of the right file. The real bhavcopy has 580 such one-character changes. It was the same mistake as the first fix, one layer up: to the command, "a cut file left this fund out" and "the right file never had this fund, a damaged copy put it there" are the same observation (stored for the day, held, not in the new file), so no rule that keeps the price in the first case can let go of it in the second. After two FAILs the case went to a different author under the owner's rule. That fix keeps nothing: every import replaces its source's day, the command prints `REMOVED` for each held price the new copy took away, says what to do in either case, and exits 1. `--accept-jumps` is about jumps only again.
- **Lesson:** "the right file undoes it" only helps if the owner knows to import it, and it only holds if nothing ever overrides "a day's file is the whole truth". A file cut short is the commonest damage there is, and it removes rather than changes, so the check for it is "nothing disappears silently", and silently is the word that matters. A protection that keeps old data against a new file is a second rule about which copy wins, and with no checksum the program cannot know which copy is the right one; when it guesses, the wrong guess is exactly the case that cannot be undone. So the program stores what the last file says and reports what that cost, and the owner, who can fetch the file again, decides. A hint is part of the contract: if following it does not recover, the hint is a bug. Empty means zero bytes: a file with bytes and no tables is damage.
- **Rule:** an import always replaces what is stored for its source and day; nothing is kept back from an earlier copy. When that removes a held fund's price, the command says `REMOVED`, names it, and exits 1, and getting the file again recovers. Every printed hint is run in a test and must end in the state it promises. A flag means one thing. A fix for one kind of damage is run against the tests of every other kind before it is pushed, with the cases built through the command the owner types, including a damaged copy that adds a held instrument its source never lists. A fuzz test of a text file without a checksum also cuts it at every line end. `prices.db` is new only when it has zero bytes.
- **Caught since:** R3 above, by the third verifier on #22, in the first version of this rule. The fourth verifier passed the current fix (PASS+NOTES) and #22 merged on 2026-11-19.

### 22. A console's code page is part of "works on the owner's OS"
- **What happened:** before handing drop 2 over, the Windows CI job was extended to run drop 2's commands on PowerShell 5.1 and 7 (#26). `stockin insights` crashed on both with `UnicodeEncodeError`: on Windows, output that is piped, captured or redirected gets the ANSI code page (cp1252), which has no ₹. Every Linux test and the Linux end-user run passed, and an interactive Windows console (already UTF-8) would have hidden it until the owner redirected output to a file or used `--json` in a script.
- **Lesson:** "it works" on one OS says nothing about the text encoding of another. The drop 1 Windows job only ran commands whose output was ASCII, so it could not see this.
- **Rule:** the CLI writes UTF-8 whatever the code page, and a test runs the CLI's `main()` in a new Python process with `PYTHONIOENCODING=cp1252` (not the installed `stockin` script itself; the Windows CI job runs that). Every owner-facing command of a sprint runs in the Windows CI job before handover (PIPELINE row 17).
- **Caught since:** this bug, by the first run of row 17.

### 23. A command the owner pastes must be one command per box
- **What happened:** when the owner asked how to install drop 2 and test it again and again, the reply listed `uv tool install …` and `uv tool update-shell` on two adjacent lines. The chat joined them into one line, the owner pasted that, and PowerShell answered `unexpected argument 'uv'`. The same happened to `stockin doctor` after the upgrade line.
- **Lesson:** PIPELINE row 14 (one command per line) is not enough, because what reaches the owner is the rendered message, not the text we wrote. Two lines in a row can render as one.
- **Rule:** every command for the owner goes in its own fenced code block, with the step to take before the next one (wait, open a new window) written outside the block. Test checklists in `/mnt/project-files/stockin/qa/` follow the same layout.
- **Caught since:** nothing yet.

### 24. A screen that explains everything in words teaches less, not more
- **What happened:** after accepting Sprint 1, the owner asked for the whole app to be redesigned as "a visual experience rather than a wall of text". Measured on the synthetic sample, the home page was about 4,000 px tall on a laptop and about 6,000 px on a phone; six of nine verdict rows repeated "No thesis yet", and each insight card carried a 60–90 word paragraph under a small chart.
- **Lesson:** the insight engine was right and the presentation buried it. Words were the main act and the charts were decoration.
- **Rule:** every block leads with a chart and a headline of at most 12 words; the longer explanation sits behind a "Why?" disclosure. Pages are built from one shared kit (`static/tokens.css`, `static/ui.css`, `templates/_ui.html`) so later sprints look the same. The owner picked direction A (Cockpit: side menu and tile grid) from three clickable options on 2026-11-22.
- **Caught since:** nothing yet; the redesign PRs are in progress.

### 25. A redesign must keep every state the old screen handled, not only the happy one
- **What happened:** the first verifier on PR #31 (home as a cockpit) FAILed it. The new Decide tile drew each verdict as a gauge and skipped verdicts with no weight. An exit on a holding with no price has no weight, so before `stockin prices fetch` (the normal state right after an import) the exit vanished from home, where the old page showed it. Reviews caused by a missing price were also counted as "need your reason", so holdings that already had a thesis were asked for one. Four injected bugs survived: no test asserted that an exit reaches home, that a review chip opens the thesis form, or that a card keeps its Why? and Learn text.
- **Lesson:** the PR's tests checked that the new charts agree with their sentences on a priced book. They never compared the new screen with the old one in the states the old one handled: no prices, damaged theses, more calls than fit.

### 26. A part that only decorates a page must never take the page's result down with it

### 26. A new store starts with the whole damage contract, not the part the last store needed first
- **What happened:** PR #29 (Sprint 2, net worth) added `assets.db` for the entries the owner types. Its first verifier FAILed it on two realistic cases. One zeroed byte at offset 104 made SQLite read an empty schema; the store treated "no tables" as a new file, wrote a fresh schema into it from a read command (`stockin asset list`), printed "nothing yet" and exited 0, so every entry and target was lost for good. This is the same case lesson 21 found in `prices.db` three days earlier, in a store written after that lesson. Separately, `asset close --on` a day before the entry's latest snapshot printed "closed" and changed nothing, and an FD's entry was dated the day it was typed, so closing a matured FD on its maturity day (what the app's own note asks for) was always ignored. The author's tests and 10 of 10 author mutations passed; the verifier's own mutations found 6 more survivors.
- **Lesson:** a lesson that lives in one module's code does not reach the next module. The new store copied the shape of `theses.db` (the newest store), not the hardest-won rules (from `prices.db`). And a command that says it did something must be tested for doing it on the case its own output steers the owner to.
- **Rule:** every store of Stockin's opens the same way: zero bytes is new; any other file must pass `PRAGMA integrity_check` and hold exactly its tables, or it is damage, and no read path ever writes a schema. A store's tests include a zeroed byte at offset 104 and a missing table. A write that would change nothing (a close dated before the latest entry) is refused with the date to use, never reported as done. A note that asks the owner to act gets a test that does exactly that and checks the result.
- **Caught since:** the round-1 fix passed its own revert check, but the second verifier FAILed #29 again on a bug that fix introduced (a value added on the day of a close was saved but not counted) plus a trigger that passed the table-name check. The third verifier passed it with notes (#29 merged) and left four surviving mutants: a reopen that ignored the label, a CLI drift column built from the raw drift, an index or view not tested, and a zero gap printed with a sign. #35 carries a test for each; #35's first verifier re-injected the reopen, the index/view and the CLI zero-gap mutants and saw them caught, the raw-drift one was not re-injected by either verifier of #35 and its test was only added in the round-2 fix, and #35 is still in verification. The rule above is also not yet true everywhere: #35's second verifier noted that the CLI read commands `stockin asset list` and `stockin networth` still create an empty `assets.db` on a fresh folder (the page no longer does).

### 28. A guard added on one path that writes a price must hold on every path
- **What happened:** PR #33 (live prices and `stockin watch`) FAILed verification three times: twice from its author, once more after the escalated fix (pipeline row 16). The escalated fix held a live price that moved more than 20% from a recent close, which stopped a 1:1 split closing at ₹750.30 against ₹1,500.55 (just above half, so the 2x rule let it through). The third verifier then imported the same split through the end-of-day file: `prices import` still used only the 2x rule, stored ₹750.30 as the close, and the next live price matched that close, passed the band, and sent a wrong ADD alert.
- **Lesson:** the band was a property of a price, not of the live path. Adding it to one writer only moved the hole to the other writer.
- **Rule:** a check on what a price may be lives in `prices.py` and is used by every path that stores or alerts on a price. A new path's tests include the case where the bad value arrives through the older path first. The band compares a price with one from the same source (an ETF's NAV and its exchange close may differ), and the 2x rule still compares across sources.
- **Then, on PR A (#38):** its first verifier FAILed it. The import now checks each price against both the best earlier price (2x) and its own source's last price (2x and the band).
